# Map Generation

`firstDocument.md` はアーカイブとして残し、このファイルを現行のMap生成仕様メモとする。

## 目的
- run中に進行するmapの生成ルールを整理する
- ノード配置、接続、出現内容、難易度カーブを定義する
- `game-loop.md` の進行仕様と `content-schema.md` のデータ定義をつなぐ

## スコープ
- normalArea の生成
- 四天王Node群 の生成
- GhostNode群 の生成
- ノード情報の事前生成
- 敵や報酬の事前配置ルール

## Map全体構造
### row構成
1. row0 : 初期パチモン選択Node
2. row1~4 : 通常Nodeのみ
3. row5~35 : 複合
4. row36 : リーグゲート
5. row37~40 : 四天王Node群
6. row41以降 : GhostNode群

### 現在方針
- run開始時に必要な範囲をまとめて生成する
- mapは行単位で進行する
- 各行には複数ノードが存在しうる

### 現在方針の補足
- ゲーム開始時に normalArea の row40 まで全生成する
- GhostNode群 は殿堂入り後に row41 以降へ追加生成する

## 共通用語
### row
- map内の進行段
- 下から上、または開始から終点へ向かって1段ずつ進む

### node
- プレイヤーが選択して進入する1地点

### edge
- node間の接続

## 生成の流れ
### run開始時
1. runSeedを決定する
2. normalAreaの骨格を生成する
3. normalAreaの各node内容を生成する
4. 保存用のmapデータに変換する

### 殿堂入り時
1. 到達時点のサーバー状態を取得する
2. row41以降のGhostNode群を生成する
3. GhostNode群の内容を固定する

### Zone定義
#### StarterZone
- 対象row: `row0`
- 役割: 初期パチモン選択
- 特殊ルール:
  - 初期パチモン選択Nodeのみ存在する
  - run開始時の味方3体をここで決定する

#### OpeningZone
- 対象row: `row1~4`
- 役割: 序盤の通常戦エリア
- 特殊ルール:
  - 通常Nodeのみ出現する
  - run序盤の立ち上がり区間として扱う

#### AdventureZone
- 対象row: `row5~35`
- 役割: run中盤の主進行エリア
- 特殊ルール:
  - 通常 / ジム / パチモンセンター / シティ が混在する
  - badge収集とビルド形成の中心区間

#### LeagueGateZone
- 対象row: `row36`
- 役割: 四天王挑戦前の判定と準備
- 特殊ルール:
  - 通常のパチモンセンターとは別扱いとする
  - 味方の回復を行う
  - 四天王挑戦条件の判定を行う
  - 条件達成時のみ次の `EliteZone` へ進行できる
  - 条件未達時は特殊敗北扱いとする
  - 後から特殊演出を追加できる余地を残す

#### EliteZone
- 対象row: `row37~40`
- 役割: 四天王Node群
- 特殊ルール:
  - 殿堂入り前の高難度連戦区間
  - 報酬はなく、各戦闘後に全味方が最大HPの20%を回復する

### NormalArea生成手順案
1. NodeとEdgeの生成
    1. Node0として初期パチモン選択Nodeを作成
    2. Node0のEdgeを3とする。
    3. 以降、最大Edge2、rowの最小column:3,最大column:6を基本（以降で設定されるシティ等は例外）として上手いこと36rowまで生成。計xNode固定（xは後で調整。仮で144Node）
    4. シティの生成
        1. row:7の隣り合う2つのNodeを統合してカナダシティに設定(Edge)
        2. row:14の隣り合う2つのNodeを統合してタマムシシティに設定
        3. row:21の...コガネシティ
        4. row:28の...ミナモシティ
        5. row:35の...トバリシティ
    5. パチモンセンターの生成
        1. row:5以降の空いてるNodeにランダムに計x個のパチモンセンターを生成
            - 連続しない
            - なるべくばらけるけど規則的になりすぎないよう上手いこと調整する
    6. LeagueGateの生成
        1. row:36をリーグゲートNode群として生成する
        2. 通常のパチモンセンターとは別種別として扱う
    7. ジムリーダーNodeの生成
        1. row:5以降の空いてるNodeにランダムに計20個生成
            - 連続しない
            - なるべくばらけるけど規則的になりすぎないよう上手いこと調整する
            - 当面の仮仕様として、計20個配置する
            - 将来的には「複数のクリア可能ルートで badge 8個以上取得可能」を保証したい
    8. 残ったNodeを通常Nodeとする
    9. row:37-40に四天王Node群を生成する

2. トレーナーとパチモンの配置
    1. ジムリーダープール(24人)からランダムな4人を四天王に設定する。
    2. ジムリーダーと四天王計24人に、得意属性が一致するパチモン(pachimonMasterにも得意属性を持たせる)をパチモンプールから3匹ずつ設定する。
    3. 作成したジムリーダーと四天王を対象Nodeにランダムに振り分ける
    4. パチモンプールの残りをランダムに各通常Nodeに振り分け、更に余ったパチモンを初期パチモン選択Nodeに配置
    5. 通常Nodeのパチモンの合計ステータスに応じて、通常トレーナーを配置（ここは厳密でなくていい）
    6. Nodeに応じてステータスと追加skill決定
        (詳細はcontent-shemaに移動する？)
        1. row毎にステータスの合計値を設定し（線形的な関数かも）
        2. 重み付けに従ってステータスをランダムに振り分ける
        3. ジムリーダー/四天王のパチモンに追加のステータス振り分け
            - 合計値と重み分けはジムリーダー/四天王が保持（ジムリーダーMaster）
        3. row毎に決められた追加skill数だけ、skill一覧からランダムに設定（重複有りの完全ランダム）

3. Modの配置
    1. 通常Mod一覧を各Nodeにランダムに振り分ける
    2. Mod効果を対象Nodeの全ポケモンに反映させる

4. 通常・ジムリーダーの報酬決定
    1. トレーナーMasterを使ってGold決定
    2. 能力報酬決定
        1. Node内のパチモンの初期スキル（2skill*3匹の6skill）からランダムに1つ決定
        2. Node内のパチモンのパッシブ（3つ）からランダムに1つ決定
        3. Modは配置されたもの
    3. ジムリーダーの場合、badge報酬を追加

### GhostNode群生成手順
Ghostのindex順に1列で並べるだけ
（Ghostが増えてきたらcolumnを増やす予定だけど、ずっと先の話）

### Ghost保存時のindex管理
完走したらindexの最後に追加する

GhostNode群で死んだ場合、現在indexの位置に割り込み、以降のGhostを後ろにずらす

同時に複数のプレイヤーが死んだ場合、上記のロジックにより、先にクリアした側が後方のindexとなる

例）
ghostが0-9まで存在しているタイミングで2人のプレイヤーがGhostNode群に到達すると、同じ並びが生成される。
先にプレイヤーAがindex3のghostに敗北した場合、index3の位置に割り込む
次にプレイヤーBが同じghostに敗北した場合、同様にindex3の位置に割り込み、先に敗北したプレイヤーAはindex3→index4となる。

## ノード接続
### 目的
- 分岐を作りつつ、行き止まりを防ぐ

### node接続アルゴリズム案
#### 案1: 親から子へ1本ずつ伸ばすシンプル生成
- 各rowのnode数を先に決める
- row `n` の各nodeから row `n+1` のnodeへ少なくとも1本つなぐ
- 子側の最大被接続数を見ながら、余った接続を追加する
- edge交差が起きる接続はスキップする

向いている点:
- 実装が最も簡単
- デバッグしやすい
- 最小プロトタイプ向き

弱い点:
- 分岐パターンが単調になりやすい
- ジム8個ルート保証のような条件を後付けしにくい

#### 案2: クリア可能ルートを先に数本作ってから肉付けする
- まず start から row36 までのクリア可能ルートを複数本生成する
- そのルート上に必要なジムやセンター配置条件を満たすよう調整する
- その後、未使用nodeと追加edgeを肉付けして自然なmapにする
- 最後にシティ統合や特殊nodeを反映する

向いている点:
- badge取得ルート保証と相性が良い
- 難易度カーブをルート単位で見やすい
- 仕様要件を満たしやすい

弱い点:
- 実装難度はやや高い
- 後から肉付けしたnodeが飾りになりやすい

#### 案3: グリッドを仮配置してから不要edgeを削る
- 各rowに3~6nodeを仮配置し、隣接可能なnode同士を一度広めにつなぐ
- そこから最大接続数や交差禁止ルールに従ってedgeを削る
- 孤立nodeや行き止まりが出たら再接続する
- 最後にシティ統合や特殊nodeへの置換を行う

向いている点:
- 見た目が自然になりやすい
- 生成後の調整ロジックを入れやすい
- 特殊node配置後の再調整と相性が良い

弱い点:
- 調整ループが増えて実装が重くなりやすい
- バグったとき原因を追いにくい

#### 案4: 土台生成 -> 特殊node配置 -> ジム保証調整
- まず各rowのnode数を決めて配置する
  - 各行に基本3node配置
  - `row0` と `row36` は1node固定
  - 合計node数を満たすまで `row2~35` に追加nodeをランダム配分する
- 次に row間接続を生成する
  - 各nodeは次rowのnodeへ最低1本接続する
  - 最大接続数は2
  - edge交差は禁止
- その後に特殊nodeを配置する
  - `row7/14/21/28/35` の横並びnodeからシティを生成する
  - シティ生成後、`row5~35` の余っているnode全てをセンター候補とみなす
  - センターを1つ配置するたびに、接続している同種nodeを次のセンター候補から外す
  - `row36` はリーグゲート固定
- 最後にジムを配置する
  - センター生成後、`row5~35` の余っているnode全てをジム候補とみなす
  - ジムを1つ配置するたびに、接続している同種nodeを次のジム候補から外す
  - ジムとセンターなど、別種類のnodeが連続するのは許可する
  - 配置後に `badge 8個以上取得可能なクリア可能ルート数` を数える
  - 条件未達ならジム配置だけやり直す

向いている点:
- シティの横並び条件と干渉しにくい
- 候補管理を単純化しやすい
- 同種node連続禁止を手順として実装しやすい
- 最後にジム条件だけ再抽選できるので調整しやすい

弱い点:
- 接続生成が弱いと、後段の配置自由度が落ちる
- ジム保証判定の実装はやや重い
- センター数やジム数が多すぎると再抽選回数が増える
